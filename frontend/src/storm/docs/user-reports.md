# Отчёты

Storm формирует документы Word (`.docx`) на основе реальных данных проекта — хостов, находок, шагов воспроизведения и приложенных доказательств. Эти данные подставляются автоматически. Разделы с жёлтыми подсказками нужно заполнить вручную в Word.

## Виды отчётов

Доступно два шаблона, заточенных под процесс сертификационных работ:

- **Отчёт для сертификации (СЗИ)** — отчёт по результатам испытаний средства защиты информации, для сертификационных испытаний.
- **Отчёт внутренней приёмки (ПП)** — протокол приёмки, для внутренней приёмки работ.

## Как сгенерировать отчёт

1. Откройте нужный проект.
2. Откройте диалог выгрузки/экспорта проекта.
3. Выберите вид отчёта — **Отчёт для сертификации** или **Отчёт внутренней приёмки**.
4. Запустите генерацию и дождитесь готовности — файл `.docx` скачается автоматически (имя файла формируется из названия проекта и вида отчёта).

Отчёт собирается из данных проекта на момент генерации: система обходит находки, подставляет их поля, разрешает файлы-доказательства по шагам и встраивает изображения в документ. Поэтому перед выгрузкой убедитесь, что находки заполнены: заголовки, CVSS, шаги воспроизведения, влияние и рекомендации, приложены нужные скриншоты.

Название продукта в отчёте и имени скачиваемого файла берётся из **affected
versions**: `Platform V Stack 1.0.2-beta.2` даёт название `Platform V Stack`
и версию дистрибутива `1.0.2-beta.2`. Одинаковые названия продуктов не
дублируются, все версии сохраняются. Если названия продукта в версиях нет,
используется название проекта. Исходные поля проекта и значения TT не меняются.

## Что попадает в отчёт

- **Находки**: в детальный перечень уязвимостей идут только реализуемые находки (**critical / high / medium / low**). Находки **info** и **unrealized** включаются только в раздел «Тесты» — как проверенные, но не являющиеся уязвимостями.
- **Таблица учётных данных**: в **отчёт СЗИ** подставляется таблица кредов проекта (логин/пароль) из вкладки **Creds**; если кредов нет — таблица остаётся пустой. (В отчёте ПП таблицы кредов нет.)
- **Ссылка на AppSec-тикет**: если у проекта задан AppSec-тикет (см. главу «Проекты»), в отчёт подставляется ссылка на него. Если ссылки нет, появится выделенная жёлтым подсказка «Заполните ссылку на APPSEC-тикет».

## Поля для ручного заполнения

В отчёте СЗИ предусмотрены подсказки для ручного заполнения:

- **4.3.1** — «Заполните результаты анализа архитектуры ПП».
- **4.3.3** — «Заполните результаты анализа модели угроз ПП».
- **4.4, Ожидаемый результат** — «Заполните ожидаемый результат» в каждой карточке теста.

Подсказки выделены жёлтым вместо многоточий. Перед использованием отчёта замените их своими результатами. Анализ поверхности атаки (4.3.2) заполняется по прежнему шаблону.

## Экспорт списков разведки

Из того же диалога, помимо Word-отчёта, можно выгрузить списки инфраструктуры — **Hosts**, **IPs** или **Endpoints**. Выгружается ровно то, что осталось на экране после наложенных фильтров, в одном из форматов: обычный **список** или **OpenAPI** (для эндпоинтов). Подробнее про OpenAPI-экспорт эндпоинтов хоста — в главе «Хосты и активы».

## Индексы находок

Уязвимости и слабости получают индекс `SA-{COMPONENT}-{DDMMYY}/{ID}`: первый компонент из списка проекта, дата окончания работ в формате день/месяц/год без разделителей, сквозной номер с `01`. Например: `SA-EVPC-201126/03`. Слабости продолжают нумерацию уязвимостей; unrealized в неё не входят. Порядок совпадает с карточками отчёта: хосты по ID, внутри хоста — критичность, затем ID находки. Если компонент или дата не заполнены, индекс содержит выделенный жёлтым плейсхолдер.

Пункт отчёта для STS вычисляется по тому же шаблону и группировке по стендам. По умолчанию используется СЗИ; администратор может выбрать ПП через `WORKS_REPORT_KIND=pp`. Индексы рассчитываются по текущему составу отчёта.
