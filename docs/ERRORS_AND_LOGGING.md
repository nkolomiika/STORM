# Ошибки и технические логи STORM

## Что видит пользователь

Неожиданная ошибка возвращает JSON с понятным `detail`, кодом `internal_error` и `request_id`. HTTP-статус сохраняется. Тот же идентификатор есть в заголовке `X-Request-ID`; его можно найти в Network браузера и затем в логах backend. HTML прокси, SQL, traceback и сообщения библиотек интерфейс не показывает.

Контролируемые ошибки валидации сохраняют безопасное бизнес-сообщение. Ошибки Pydantic преобразуются в подсказки о поле без `input`, `ctx.error` и полного представления модели. Сбои интеграций используют стабильные коды: `mail_not_configured`, `mail_unavailable`, `mail_auth_failed`, `task_tracker_not_configured`, `task_tracker_unavailable`.

`frontend/src/errorMessages.ts` содержит тексты по кодам. `getApiErrorMessage` скрывает неизвестные 5xx и нативные исключения, но пропускает безопасные бизнес-ошибки 4xx. Для намеренных локальных проверок используется `UserInputError`; произвольный `Error.message` нельзя отдавать в уведомление. Локализация выполняется `t()` при показе.

Не вставляйте в пользовательский ответ `str(exc)`, `response.text`, SQL или настройки интеграции. Подробности записывайте в технический лог и возвращайте контролируемое сообщение. Внешние ответы могут содержать секреты, поэтому печатать их целиком тоже нельзя.

## Почта

Создание приглашения, повторная отправка, восстановление и административный сброс пароля проверяют, включена ли почта, заполнен ли SMTP host и допустим ли порт. При отсутствии настройки возвращается 503 и `mail_not_configured` с сообщением «Отправка писем пока не настроена. Обратитесь к администратору». Проверка выполняется до поиска email при восстановлении пароля, чтобы ответы не раскрывали существование учётной записи.

Успешный запрос означает постановку письма в очередь. Интерфейс сообщает именно это, а не обещает доставку. Сетевой сбой или ошибка SMTP/OAuth могут возникнуть позже, в worker.

`mail_worker` сохраняет безопасный код доставки в payload задания; сырой `last_error` пользователю не возвращается. `/users/invitations` получает последнее задание каждого приглашения одним оконным запросом и возвращает `email_status`, `email_error_code`, `email_error`. Старые записи с `last_error` без кода получают общее безопасное сообщение. Состояние `sent` очищает ошибку. После переотправки учитывается новое задание, а не старое неуспешное.

Страница Members обновляет список раз в 15 секунд, показывает понятную ошибку рядом с приглашением и одно всплывающее уведомление на обнаруженный сбой. Секреты, тело письма и ссылка активации не входят в этот ответ. Публичное восстановление пароля сохраняет одинаковый ответ для существующего и неизвестного email.

Почтовый worker должен быть запущен отдельно; API не устанавливает SMTP-соединение синхронно при каждом запросе. Наличие имени SMTP-сервера ещё не подтверждает доступность сервера или правильность учётных данных.

## Какие логи собирать

```bash
docker compose logs --since 30m backend
docker compose logs --since 30m mail-worker
docker compose logs --since 30m recon-worker
```

Ищите сначала `request_id` запроса. Основные события:

| Событие | Контекст |
| --- | --- |
| `request_completed` | Метод, шаблон маршрута, HTTP-статус, actor ID, длительность |
| `unexpected_error` | Request ID, класс исключения, traceback с маскированием секретов |
| `request_validation_failed` | Число ошибок и типы проверок без значений полей |
| `audit_prepared` / `audit_committed` | Действие, actor ID, вид и ID сущности; prepared ещё не означает commit |
| `mail_enqueued` / `mail_enqueue_failed` | Job ID, шаблон, инициатор, статус очереди |
| `mail_delivery_failed` / `mail_delivered` | Job ID, шаблон, номер попытки, предел попыток, безопасный код, длительность |
| `task_tracker_request` | Операция нативного API, метод, статус, длительность |
| `sts_export_reused` | Проект, находка и инициатор повторного экспорта |

Для фоновых задач основная связь — `job_id`: найдите постановку с request ID в backend, затем попытки этого job ID в логах worker. HTTP-контекст не предполагается автоматически доступным в другом процессе.

## Защита логов

`observability.configure_logging` добавляет фильтр к существующим обработчикам без сброса конфигурации. Он маскирует пароли, Bearer/Basic, OAuth-токены, cookie, пароли в URL подключения и токены публичных auth-ссылок, в том числе внутри traceback. Исходный URL access-лога Uvicorn заменяется отсылкой к безопасному шаблону маршрута в `storm.http`. Query string, HTTP-тело и cookie в журнал запросов не включаются.

SQLAlchemy создаётся с `hide_parameters=True`: параметры запросов не печатаются даже при включённом SQL echo. Не включайте вывод payload писем или сырых ответов внешних систем отдельным logger — фильтр не заменяет минимизацию записываемых данных.

Хранение, ротация, срок удаления и доставка логов в централизованное хранилище задаются окружением. Этот проход не подключает внешний сборщик. Встроенные аудит-события БД и технический лог решают разные задачи.

## Проверки

Регрессионные тесты покрывают отключённый/пустой SMTP, отсутствие частично созданного приглашения, одинаковые ответы восстановления, ошибки соединения и авторизации worker с последующим успешным повтором, выбор последнего задания, маскирование секретов, безопасные 500 и связь с request ID. Реальные SMTP, OAuth, Task Tracker и RabbitMQ заменены моками.
