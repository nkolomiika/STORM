# Проверка IDOR — 17 ноября 2026

Проверены HTTP-границы проектов, вложенных объектов, файлов, уведомлений и
агентского API. Тесты работают с PostgreSQL и настоящими зависимостями доступа;
пользователь — обычный участник проекта A без доступа к проекту B.
Администратор для отрицательных проверок не используется.

## Найденная ошибка

GET связи уязвимости с STS проверял доступ к проекту из URL, но искал саму связь
только по vulnerability_id. Участник A мог подставить ID уязвимости B под URL
проекта A и получить чужую ссылку STS; при настроенном TT мог запускаться
внешний запрос синхронизации статуса.

`WorksService.get_link` теперь принимает project_id и сначала проверяет
принадлежность уязвимости проекту. Для чужого объекта возвращается 404 до
создания клиента TT. Отдельная регрессия запрещает любое обращение к клиенту
при таком запросе.

## Матрица регрессий

| Сценарий | Ожидаемое поведение |
| --- | --- |
| 90 операций всех project-маршрутов OpenAPI v1 с project_id B | 403 до чтения или изменения данных |
| 21 подстановка ID дочернего объекта B в URL проекта A | 404, без чужих данных |
| Скачивание файла B | 403 до хранилища |
| Чужое уведомление / отметить все свои прочитанными | 404 / уведомления B остаются непрочитанными |
| Agent token, ограниченный проектом A | A доступен, B — 403, чужой дочерний объект — 404 |
| Подмена уязвимости в связи STS при включённом TT | 404, внешний клиент не вызывается |

Вложенная матрица включает хосты, порты, сервисы, эндпоинты, заметки,
уязвимости, комментарии, файлы, credentials и задания ферм. Перед запросом
проверяется существование маршрута и метода: случайный 404 от опечатки не
считается успешной проверкой доступа. Проектная матрица строится из OpenAPI,
поэтому добавленный маршрут попадёт в проверку автоматически.

Команда воспроизведения:

```bash
docker compose exec -T \
  -e STORM_TEST_DATABASE_URL=postgresql+asyncpg://user:password@db:5432/storm \
  backend python -m pytest tests/api/test_idor_audit.py -q
```

Набор содержит 114 тестов. Дополнительные проверки авторизации находятся в
существующих test_access_control, test_security_audit и тестах Agent API.
Это проверка текущей модели доступа; она не доказывает отсутствие будущих
ошибок и не заменяет согласование прав при добавлении нового вида сущности.
