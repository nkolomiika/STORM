# Дублирование, устаревший код и документация STORM

Дата: 15 ноября 2026 года. Проверенная версия: `4a1988a` (`init`), включая изменения `0db99bf` и фавикон `8ffc8ad`.

## Исправления 16 ноября 2026 года

Выполнена очистка прикладного кода:

- Объединены все пять найденных групп дублирования: `endpoint_fields.py`, `entity_access.py` и `farm/job_access.py` содержат общие операции. Обработчики ошибок StormError также используют одну реализацию.
- Удалены 35 неиспользуемых функций frontend API и пять констант, четыре локальные функции и импорт, шесть старых backend-методов, схема прямого создания пользователя и заглушка IAM. Сброс временного пароля сохранён; проверки пароля перенесены на действующий сценарий принятия приглашения.
- Удалён отдельный Cloudflare-флаг, вычислявшийся без потребителей. Распознавание Cloudflare как технологии сохранено.
- Опрос заданий вынесен в `useReconJobPolling`: отмена устаревшего ответа, повтор после сбоя, одно уведомление до восстановления соединения; ограничение частоты обновления JS сохранено.
- У STS-экспорта один интерфейсный поток. Backend блокирует строку находки и возвращает существующую связь при повторном/параллельном запросе. Сценарий с двумя конкурентными запросами проверен с MockTransport.
- Неожиданные исключения и технические ответы скрываются централизованно. Отключённая/неполная почта даёт понятную ошибку до изменения данных; очереди не выдаются за доставку. В Members показываются безопасные статусы и ошибки писем.
- Добавлены `X-Request-ID`, длительность, шаблон маршрута и actor ID в HTTP-логах. Логи сохраняют traceback; секреты и URL-токены маскируются. SQL-параметры скрыты, тела ответов OAuth и Task Tracker не печатаются. По job ID можно связать запрос отправки письма с попыткой воркера.
- Добавлены содержательные комментарии к основным изменённым бизнес-операциям и обновлён каталог методов. Компилятор теперь проверяет неиспользуемые локальные функции и параметры при обычной сборке.

Проверки статических кандидатов после очистки: точных дубликатов тел Python-функций размером от 35 AST-узлов — 0; экспортов значений frontend без production-потребителей — 0. Это результат ограниченных алгоритмов, а не утверждение об отсутствии любого сходного кода.

Ниже сохранён первоначальный аудит версии `4a1988a`; ссылки на исходники закреплены за этой версией. Числа и замечания в исторической части относятся к состоянию до исправлений. Полная ручная документация всех методов не заявляется: генерируемые контракты остаются частью справочника. Историческую совместимость схемы/startup и старых клиентов в этом проходе не удаляли.

## Результат

Дублирование и неиспользуемый код есть. Каталог методов полный в заявленной области `backend/app` и `frontend/src`, но полноценные описания поведения написаны не для каждого метода. Актуальность сгенерированных файлов не равнозначна полноте ручной документации.

Проверка охватила 70 Python-файлов приложения, 35 исходных модулей frontend, каталог методов и обе OpenAPI-схемы. Выполнены разбор AST, проверка ссылок TypeScript через компилятор, поиск вызовов в приложении/тестах/скриптах и ручная сверка найденных мест. Внешние системы не вызывались. Прикладной код и схема БД в рамках аудита не изменялись.

## Подтверждённое дублирование

### Два UI-потока экспорта в STS

[StormApp.tsx:5355](https://github.com/nkolomiika/STORM/blob/4a1988a/frontend/src/storm/StormApp.tsx#L5355) показывает «Export to AppSec» при настроенном Works и отсутствии связи. Рядом [StormApp.tsx:5359](https://github.com/nkolomiika/STORM/blob/4a1988a/frontend/src/storm/StormApp.tsx#L5359) показывает «Export to Task Tracker». Обе кнопки относятся к одной находке и ведут в одну интеграцию:

- Прямой путь: `exportToWorks` → `exportVulnerabilityToWorks`.
- Путь с окном: `openTaskTrackerExport` / `doTaskTrackerExport` → `exportVulnerabilityToTaskTracker` → `exportVulnerabilityToWorks`.

Адаптеры [api.ts:1052](https://github.com/nkolomiika/STORM/blob/4a1988a/frontend/src/api.ts#L1052) преобразуют `WorksIssueLink` в `TaskTrackerIssueLink`; отдельной второй интеграции здесь нет. В пути Task Tracker есть предварительное чтение существующей связи; у обработчиков разные состояния загрузки и результата. Поэтому это уже два поддерживаемых сценария одной операции, а не только два названия.

[WorksService.export_vulnerability:400](https://github.com/nkolomiika/STORM/blob/4a1988a/backend/app/services.py#L400) при вызове создаёт внешний тикет и затем сохраняет/перезаписывает локальную связь. Само предварительное чтение в клиенте не гарантирует идемпотентности повторного или конкурентного запроса. Возможность повторного создания следует отдельно согласовать и проверить с замоканным клиентом; фактическое появление дублей на проде в этом аудите не проверялось.

Каталог явно исключает тесты, анонимные callbacks, скрипты обслуживания и Alembic-миграции. В `backend/scripts` есть 48 объявленных функций, из них 12 с docstring; в 26 файлах ревизий миграций — 50 функций. Скрипты описаны на уровне сценариев в руководстве, но отдельной карточки для каждого их метода нет. Поэтому утверждение «каждый метод всего репозитория содержательно документирован» неверно.

### Устаревшие или неточные описания

1. `createUser` ссылается на отсутствующий `pages/UsersAdminPage.tsx`.
2. [routers/users.py:215](https://github.com/nkolomiika/STORM/blob/4a1988a/backend/app/routers/users.py#L215) и [frontend/api.ts:245](https://github.com/nkolomiika/STORM/blob/4a1988a/frontend/src/api.ts#L245) обещают поиск пользователей в IAM. [UserService.iam_user_candidates:847](https://github.com/nkolomiika/STORM/blob/4a1988a/backend/app/services.py#L847) остаётся заглушкой и возвращает `[]` как при отключённом, так и при настроенном SSO. Это отсутствие реализации, а не ошибка конфигурации внешней системы.
3. Комментарии `farm/fingerprint.py` и `farm/__init__.py` по-прежнему описывают отдельный CF-флаг, хотя его сохранение и отображение уже удалены.
4. Проверка `--check` обнаруживает рассинхронизацию генерации, но не такие смысловые ошибки: неточный docstring тоже попадёт в актуальную сгенерированную документацию.

## Историческая совместимость, которую нельзя удалять вслепую

- `Project.appsec_version_code/name` поддерживают старых клиентов как представление первой версии. Каноническое поле — массив `appsec_versions`; совместимость зафиксирована кодом и тестами.
- Старые имена/статусы в Alembic и архивированных документах являются историей обновления, а не действующей интеграцией с Jira.
- Поддержка старых записей Markdown, JWT/password hashes и шаблонов Word имеет работающих потребителей. Само слово `legacy` не является причиной удаления.
- [startup:197](https://github.com/nkolomiika/STORM/blob/4a1988a/backend/app/main.py#L197) дублирует часть изменений схемы из Alembic: например, удаление `projects.description` есть и в startup, и в ревизии 0025. Это уже отмеченное архитектурное ограничение. Перед переносом нужна проверка реально применённых ревизий стендов; простое удаление startup-веток может сломать обновление старой БД.

## Воспроизводимые проверки

Из корня проекта:

```bash
node frontend/scripts/export-methods.mjs > /tmp/storm-audit-methods-ts.json
python3 backend/scripts/export_method_docs.py --frontend-json /tmp/storm-audit-methods-ts.json --check
```

Из `frontend`:

```bash
./node_modules/.bin/tsc --noEmit -p tsconfig.app.json --noUnusedLocals --noUnusedParameters
```

Вторая команда сейчас ожидаемо возвращает пять диагностик выше. Это дополнительная проверка, а не результат обычной сборки или тестов. Полный тестовый набор заново не запускался: прикладной код не менялся. Для точных дублей использовалось сравнение AST тел Python-функций; для экспортов frontend — TypeScript checker с разрешением import aliases и исключением тестов. Кандидаты сверены поиском по исходникам и тестам.
