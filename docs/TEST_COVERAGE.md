После успешного повторного прогона владелец отдельно разрешил push в GitHub; это разрешение не означает достижения полного покрытия. Все шесть согласованных дефектов из [архитектурного ревью](ARCHITECTURE_REVIEW.md) исправлены. Дополнительные находки, исправления безопасности и остаточные риски описаны в [аудите безопасности](SECURITY_AUDIT.md).

Vitest включает все `src/**/*.{ts,tsx}`, в том числе не импортированные тестами модули. Исключены только сами тесты, setup и декларации типов. На фронтенде нет исключения большого StormApp или API-клиента из знаменателя.

## Граница внешних систем

Из отдельного показателя backend исключены только явно перечисленные адаптеры: Cloudflare, SMTP/OAuth доставки почты, RabbitMQ publisher и mail worker, OIDC, Works, MinIO client, роутеры Jira/Works, классы Jira/Works в services.py и методы SSO provisioning. Точный список зафиксирован в [скрипте](../backend/scripts/coverage_audit.py) и JSON-отчёте.

Внутренние проверки доступа, CRUD и оркестрация ферм остаются в знаменателе. Сетевые вызовы в существующих unit-тестах интеграций подменены. В ходе прогона не запускались реальные сканы, TruffleHog, httpx-pd, SMTP, SSO, Works/Jira, RabbitMQ worker или MinIO-операции. PostgreSQL используется локально для воспроизведения ошибок ORM и ограничений БД.

## Что добавлено при проверке

Добавлено 68 frontend-сценариев: полная логика auth store, расчёт CVSS 4.0 и границы severity, безопасность Markdown URL, обработка ошибок API, однократный refresh, общий refresh для конкурентных запросов, отказ refresh и ограничения повторной попытки, контракты заметок/комментариев. `store.ts` и `cvss.ts` достигают 100% строк и ветвей.

Следующий этап увеличил набор с 753 до 915 backend-тестов и с 204 до 235 frontend-тестов. Добавлены реальные проверки PostgreSQL на откат данных вместе с аудитом, конкурентное использование одноразовых ссылок, пагинация всех находок, запрет агентского доступа заблокированному владельцу, очистка notes и сохранность дерева заметок. Враждебные запросы проверяют неверные JSON-типы, NUL, NaN, переполнение ID, повреждённую кодировку, глубину вложения, SQL-текст, mass assignment, файлы и YAML. Корпус из 250 документов для парсеров — один отдельный unit-тест, а не 250 HTTP-тестов.

В setup UI-тестов установлен транспортный запрет на незамоканные HTTP-запросы. Раньше 78 тестов перехватывали ошибки соединения и оставались зелёными; теперь такие запросы приводят к падению проверки даже при catch в компоненте. Недостающие фикстуры заданы явно в тестах App, Root, Roles и Login. Запрет не отключает тестирование реального API-клиента: его отдельные тесты используют собственный in-memory Axios adapter.

## Командные инъекции через хост и JS

В проверенных путях приложения командная инъекция не воспроизведена:

- Все пять мест запуска внешних процессов используют `asyncio.create_subprocess_exec`, без shell, `os.system`, `popen` и строковой сборки команды.
- ProjectDiscovery httpx-pd получает фиксированные аргументы, список целей передаётся только через stdin. Хост не определяет исполняемый файл и не добавляет CLI-флаги.
- Python-библиотека httpx выполняет HTTP-запросы, а не shell-команды.
- TruffleHog получает `filesystem`, случайный абсолютный путь `stormjs-*.js` и фиксированные флаги. Имя хоста и JS-текст не попадают в argv. JS записывается как данные и не запускается.
- Путь бинаря и путь конфигурации берутся из серверных Settings. Загруженный хост не управляет этими параметрами. Конфигурация с символом `;` всё равно передаётся одним аргументом.
- Парсер целей фермы отклоняет командные символы в hostname и строки, похожие на CLI-флаги. CRUD-схемы хостов не являются строгим DNS-валидатором; само сохранение строки не означает её выполнение.

[Регрессии](../backend/tests/test_command_injection.py) проверяют `;`, `&&`, pipe, обратные кавычки, `$()`, перенос строки, encoded control characters и option-like значения. Подменённый запуск проверяет argv/stdin и очистку временного JS-файла. Дополнительный локальный Python-процесс возвращает входные аргументы буквально; временный маркер не создаётся. Реальные бинарные сканеры и сторонние сервисы не вызываются. Проверка относится к способу запуска в STORM; она не является аудитом реализации самих сторонних бинарей или полной проверкой SSRF.

## Агентские токены заблокированного пользователя

Дефект исправлен после указания владельца исправлять все найденные ошибки: `get_agent_token_context` проверяет существование, активность и блокировку создателя до обновления last_used_at. Регрессии подтверждают 401 при чтении и записи, а также отсутствие побочных изменений при отказе. Несуществующие project_id и expires_at без timezone отклоняются с 422 до записи токена.

## Воспроизведение покрытия

Из корня репозитория при запущенной локальной БД:

```bash
docker compose exec -T backend python -m pip install -r requirements-test.txt
docker compose exec -T \
  -e STORM_TEST_DATABASE_URL=postgresql+asyncpg://user:password@db:5432/storm \
  -e COVERAGE_FILE=/tmp/storm-audit.coverage \
  backend python -m coverage run -m pytest -q --tb=short
docker compose exec -T \
  -e COVERAGE_FILE=/tmp/storm-audit.coverage \
  backend python -m coverage json -o /workspace/backend/coverage/coverage.json
```

Далее в `frontend`:

```bash
npm ci
npm run test:coverage
npm run build
```

И снова из корня:

```bash
python3 backend/scripts/coverage_audit.py \
  --backend backend/coverage/coverage.json \
  --frontend frontend/coverage/coverage-summary.json \
  --output docs/testing/coverage-summary.json
```

Полные локальные отчёты и HTML исключены из git через `.gitignore`; в репозитории остаётся компактная сводка без абсолютных пользовательских путей.
