# Нагрузочное тестирование и оптимизация STORM

Замеры выполнены 10 ноября 2026 года на локальном Docker-стенде, Python 3.12, PostgreSQL 16. Проверено внутреннее HTTP-чтение через настоящий TCP/Uvicorn с аутентификацией и SQLAlchemy. Внешние интеграции и startup отключены. Существующие таблицы приложения не использовались: каждый прогон создаёт и удаляет собственную схему `perf_<uuid>`.

## Данные и методика

Основной набор: **5 000 хостов, 5 000 IP, 20 000 портов, 20 000 сервисов, 100 000 эндпоинтов, 5 000 находок, 5 000 JS-файлов, 1 000 комментариев и 1 000 уведомлений**. У хоста 20 эндпоинтов с headers/query/body; у порта один сервис. У комментариев есть упоминания. Уведомления нагрузочного сценария — события добавления в проект; смешанные контексты отдельно проверяются функциональным тестом.

Для прямого сравнения: 30 измеренных запросов на сценарий, до 8 одновременно, один предварительный прогрев. Сценарии выполняются последовательно, запросы внутри сценария — параллельно. Измеряется клиентская HTTP-задержка после получения семафора, без времени ожидания в очереди генератора; RPS учитывает всё время выполнения серии. p95 — ближайший верхний ранг отсортированных задержек. При 30 образцах это диагностический показатель, а не устойчивый production SLA.

Код считает SQL на запрос через ContextVar и события SQLAlchemy. `sql_ms_avg` включает время ожидания выполнения/возобновления корутины под конкуренцией, поэтому это не чистое CPU-время PostgreSQL. Для анализа отдельных запросов отдельно снят `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`.

Процесс API, HTTP-клиент и генератор находятся в одном контейнере; сервер — один worker, пул 5 + 10 overflow. PostgreSQL — соседний compose-контейнер. Это тёплый локальный тест без TLS/nginx, пользовательского браузера, длительной фоновой нагрузки и внешних сетевых ожиданий. Подготовка данных выполняет ANALYZE. Числа нельзя использовать как оценку ёмкости промышленного развёртывания.

| 200 хостов | 9 → 9 | 1 001,97 → 1 091,12 | 2 564,65 → 2 248,65 | 7,10 → 7,39 |
| Порты хоста | 9 → 5 | 50,48 → 46,60 | 84,46 → 68,08 | 128,49 → 146,66 |
| Эндпоинты хоста | 8 → 4 | 52,44 → 45,96 | 79,42 → 59,65 | 128,60 → 154,04 |

Все 270 запросов в каждом из сравниваемых прогонов вернули 200. Число запросов комментариев/уведомлений сократилось независимо от сетевого шума; p95 снизился примерно на 54% и 66%. У JS осталось столько же SQL, но lookup хостов теперь ограничен текущей страницей, а не всем проектом.

Список находок получил один дополнительный общий SQL-запрос и поле `affected_host_id` — ответ вырос примерно с 38,5 до 40,7 КБ. Его медиана отдельно стала выше. Взамен UI больше не делает запрос полной карточки для каждой из 100 строк; это подтверждено UI-тестом, но время полной загрузки экрана в браузере отдельно не измерялось.

Для списка 200 хостов большого ускорения нет: p50 даже вырос в этом прогоне, а p95 немного снизился. Ответ по-прежнему содержит около 2,1 МБ и 6 000 ORM-сущностей. Менять размер пула вместо ограничения этого объёма недостаточно. Колебания статистики проектов также не трактуются как отдельная оптимизация: его SQL не менялся.

| Порты | 226,73 | 207,88 |
| Эндпоинты | 194,25 | 255,47 |

При росте конкуренции пропускная способность hosts_200 почти не растёт, а задержка увеличивается: это оставшийся предел текущего объёма графа и одного процесса, с ожиданием пула при 24 клиентах. Для интерпретации нужны также CPU-профиль и объём ответа; данные не доказывают, что PostgreSQL исчерпал ресурсы.

Peak RSS процесса: 232,64 МБ в baseline, 231,14 МБ в итоговом c8, 341,58 МБ в c24. Это общий пик с генерацией тестовых данных и HTTP-клиентом в том же процессе, а не измерение памяти одного API-запроса или production worker.

## Индексы и профиль

До индексов: [before-indexes-5000.json](performance/before-indexes-5000.json). После: `query_plans` в [итоговом прогоне](performance/final-5000-c8.json).

| Запрос | До | После |
| --- | --- | --- |
| Порты host_id=1 из 20 000 | Seq Scan, отфильтровано 19 996 строк, 0,476 мс | Index Scan `ix_ports_host_id`, 0,020 мс |
| Сервисы 80 портов из 20 000 | Seq Scan, отфильтровано 19 920 строк, 0,820 мс | Index Scan `ix_services_port_id`, 0,049 мс |

Созданы индексы по FK и concurrent-миграция `0020`; upgrade/downgrade проверены реальным PostgreSQL-тестом. Эти короткие времена относятся к локальным тёплым данным; ускорение SQL не равно такому же ускорению всего HTTP-ответа.

Диагностический cProfile: [profile-host-list.json](performance/profile-host-list.json). На один прогрев и три запроса hosts_200 приходится 24 008 вызовов ORM `_instance`. Профилирование само добавляет накладные расходы, а весь профиль включает seed/import; результаты задержки этого прогона не используются в таблице сравнения. При необходимости профиль пересоздаётся командой ниже.

## Дополнение: лёгкая загрузка дат для графиков проектов

На главной странице проектов график хостов использует только `created_at`, но раньше вызывал `getHosts` и вычитывал все полные деревья. Теперь `GET /projects/{project_id}/host-creation-times` выбирает только даты одним SELECT. Состав сохраняется: включены `origin=ip`, повторяющиеся даты и тот же порядок; доступ ограничен тем же `require_project_access`.

Сравнение в **одной временной схеме** на 5 000 хостов / 100 000 эндпоинтов, 8 загрузок каждого варианта, конкуренция 4: [project-chart-hosts-5000-c4.json](performance/project-chart-hosts-5000-c4.json).

| На одну загрузку дат хостов проекта | Раньше: все страницы деревьев | Теперь: только даты |
| --- | --- | --- |
| HTTP-запросы | 25 | 1 |
| SQL, включая авторизацию | 225 | 3 |
| Объём ответов | 52 830 161 байт | 150 001 байт |
| p50 | 14 820,92 мс | 25,36 мс |
| p95 | 15 955,03 мс | 50,54 мс |

Число дат (5 000) и SHA-256 их сериализованного списка совпали. Все 200 измеренных HTTP-запросов прежнего варианта и 8 нового вернули 200. Объём сократился примерно в 352 раза. Это измерение части загрузки графиков через HTTP с разбором JSON, а не ускорение всего приложения; выборка из 8 повторов мала для оценки SLA. Данные находок и их текущая пагинация этим изменением не затронуты.

Дополнительно `endpointRows` и `endpointGroups` в UI мемоизированы: создание объектов и фильтрация эндпоинтов не повторяются при изменениях несвязанных полей редактора. При смене хостов, фильтров или раскрытых групп результат пересчитывается. Отдельный количественный выигрыш этой мемоизации не заявляется.

Повторить оба варианта на одних данных:

```bash
docker compose exec -T \
  -e STORM_TEST_DATABASE_URL=postgresql+asyncpg://user:password@db:5432/storm \
  backend python scripts/benchmark_internal_api.py \
  --hosts 5000 --requests 8 --concurrency 4 --scenario chart_hosts_compare \
  --label repeat-chart --output /workspace/docs/performance/repeat-chart.json
```

## Как повторить

Из корня, при запущенных backend и PostgreSQL:

```bash
docker compose exec -T \
  -e STORM_TEST_DATABASE_URL=postgresql+asyncpg://user:password@db:5432/storm \
  backend python scripts/benchmark_internal_api.py \
  --hosts 5000 --endpoints-per-host 20 --requests 30 --concurrency 8 \
  --label repeat --output /workspace/docs/performance/repeat-5000-c8.json
```

Для конкуренции 24: `--requests 100 --concurrency 24`. Для одного сценария: `--scenario hosts_200`. Без явного test DSN скрипт завершается; набор ограничен аргументами CLI. Ошибки HTTP сохраняются в JSON и приводят к ненулевому exit code. Схема удаляется в finally; принудительный kill процесса может оставить perf-схему, поэтому завершайте прогон штатно.

```bash
node frontend/scripts/benchmark-host-index.mjs

docker compose exec -T \
  -e STORM_TEST_DATABASE_URL=postgresql+asyncpg://user:password@db:5432/storm \
  backend python -m cProfile -o /tmp/storm-host-list.prof \
  scripts/benchmark_internal_api.py --hosts 5000 --requests 3 --concurrency 1 \
  --scenario hosts_200 --label profile \
  --output /workspace/docs/performance/profile-host-list.json

docker compose exec -T backend python -c \
  "import pstats; pstats.Stats('/tmp/storm-host-list.prof').sort_stats('cumulative').print_stats(40)"
```

Опция `--review-findings` исторически использовалась для воспроизведения логических дефектов в собственной схеме. Она намеренно имитирует отказ аудита и создаёт конфликт переноса дочерней заметки; HTTP 500 в сохранённом [logical-reproductions.json](performance/logical-reproductions.json) относится к состоянию до исправлений 13 ноября. Сейчас отказ аудита откатывает запись, конфликт заметок возвращает 409, notes=null очищает поле. Актуальные ожидания закреплены в test_review_regressions.py; диагностический режим бенчмарка не подменяет эти регрессии.
