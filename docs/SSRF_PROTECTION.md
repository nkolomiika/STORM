# Защита от SSRF в STORM

## Что найдено и исправлено

Прежний HTTP transport сначала проверял DNS, затем библиотека разрешала имя ещё
раз при соединении. Это оставляло DNS rebinding/TOCTOU. Внешние httpx-pd,
whatweb, nmap, subfinder и trufflehog подключались самостоятельно; повторная
проверка имени перед запуском не устраняла эту гонку. Опция приватных целей
могла отключить прикладную проверку. Сетевого барьера контейнера не было.

Теперь сетевой backend Python проверяет **все** адреса A/AAAA и передаёт в socket
только выбранный публичный IP. Имя остаётся origin пула, Host и TLS SNI;
повторного DNS при подключении нет. Новое соединение и каждый переход redirect
проходят тот же контроль. Ограничены redirect и размер JS. Источник crt.sh также
использует этот transport. Unix-сокеты сканеру не предоставляются.

Отсекаются частные адреса, loopback, link-local, metadata, CGNAT, служебные,
неопределённые, multicast и переходные IPv6/NAT64-адреса. Частично приватный
DNS-ответ отклоняется полностью. `FARM_ALLOW_PRIVATE_TARGETS=true` больше не
принимается. Private PTR-запросы не выполняются. Для приватного и неразрешаемого
имени выдаётся одна безопасная ошибка без найденного IP.

## Контейнерный барьер

Неизменяемый entrypoint образа ставит `iptables`/`ip6tables` OUTPUT-chain
`STORM_EGRESS` до приложения. При ошибке правил или DNS доверенных интеграций
приложение не стартует. Затем `setpriv` удаляет NET_ADMIN/NET_RAW из bounding set,
включён no-new-privileges. Правила применяются отдельно в namespace каждого
backend/worker, host firewall не изменяется. Host network и privileged не нужны.

Внешние инструменты запускаются через `scanner_options` как UID 65532 без групп,
capabilities и секретов окружения. HTTP proxy из окружения им не передаётся.
Временный JS-файл отдаётся только этому UID с режимом 0600. Nmap использует TCP
connect scan `-sT`; raw-сокеты не требуются. HTTP/сервисные ответы от внутренних
адресов сканер не получает — блокируется само соединение, включая blind SSRF.

Приложение сохраняет точечные разрешения IP+TCP-порт для БД, MinIO, RabbitMQ,
настроенных TT/IAM/SMTP. Правила owner UID 0 не распространяются на инструменты.
Разрешения зависят от процесса: backend использует БД/очередь/MinIO/TT/IAM,
mail-worker — БД/очередь/SMTP/OAuth, recon-worker — БД/очередь. Workers не
требуют DNS неиспользуемых веб-интеграций при старте.
Python-функции сканирования также не используют эти исключения: их transport
отклоняет внутреннюю цель до соединения. Metadata/loopback не разрешаются даже
через список доверенных интеграций. DNS разрешён только настроенным резолверам.
IPv6 neighbor discovery разрешён для работы публичного IPv6; произвольный
ICMP-скан внутренних адресов инструментам недоступен.

Дополнительные адреса IAM token/JWKS или прокси указываются DevOps в
`STORM_TRUSTED_EGRESS`, JSON-массив точных URL. Это доверенная конфигурация,
не пользовательский allowlist и не разрешение приватных сканов. IP интеграций
фиксируются при старте: после смены их DNS/IP пересоздайте контейнеры.

## Проверки

```bash
# Нужен пересобранный контейнер с установленным firewall.
docker compose exec -T -e STORM_SCANNER_SANDBOX=1 backend python -m scripts.check_egress
```

Smoke сначала убеждается в наличии обеих OUTPUT-chain, затем проверяет
непривилегированный дочерний процесс: настоящий открытый loopback-порт,
закрытый loopback-порт, существующая БД, неиспользуемый приватный адрес,
metadata IPv4/IPv6. Во всех внутренних попытках соединения нет; UID=65532,
CapEff=0, NoNewPrivs=1. При этом БД доступна приложению и публичный TCP
`1.1.1.1:443` доступен инструменту. Приватные проверки не отправляют HTTP-запрос
и не считывают содержимое сервисов. Изменений host firewall тест не делает.

Юнит/API-тесты подменяют DNS/сокет и проверяют отсутствие вызова connect для
private/mixed/empty DNS, отсутствие второго разрешения имени, повторную проверку
соединений, неразличимый безопасный результат DNS-отказа, отсутствие private PTR,
очистку env и единый формат ошибок. Реальные сканеры во внешние системы в этих
тестах не запускаются.

Эта граница относится к поддерживаемому контейнерному запуску. Запуск Python
напрямую на хосте не устанавливает контейнерные правила. Не монтируйте Docker
socket внутрь приложения и не переопределяйте entrypoint. При обновлении нужен
`up --build --force-recreate`, одного restart недостаточно.

Сетевые попытки блокируются независимо от наличия внутреннего сервиса. Тесты
не обещают одинаковое полное время любого HTTP-запроса под разной нагрузкой;
критично, что приложение не получает ответ от проверяемого внутреннего сервиса.

Основания: [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html),
[Docker networking](https://docs.docker.com/engine/network/),
[Docker security](https://docs.docker.com/engine/security/).
