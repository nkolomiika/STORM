# Task Tracker: STS и APPSEC

Приложение использует нативный API Task Tracker/Works и настройки `WORKS_*`.

| Операция | Пространство | Код и связь |
| --- | --- | --- |
| Экспорт уязвимости | `WORKS_SPACE=STS` | POST `WORKS_CREATE_PATH`, тип `bug_appsec`; верхний space=STS, attributes.space=APPSEC по нативному контракту |
| Раздел Tasks и поиск тикета для проекта | `WORKS_TASKS_SPACE=APPSEC` | POST `WORKS_TASKS_SEARCH_PATH`; в выдаче допускаются только ключи `APPSEC-<число>` |
| Карточка задачи | APPSEC | GET `WORKS_UNIT_DETAIL_PATH` (`/rest/api/unit/v2/{key}`), `validatorEnabled=true`; другой префикс ключа отклоняется до сети |
| Привязка проекта | APPSEC | `projects.appsec_ticket_key` и `appsec_ticket_url`; это тикет запроса на анализ, а не экспортированная уязвимость |
| Связь после экспорта | APPSEC → STS | POST `WORKS_LINK_PATH`: `source=project.appsec_ticket_key`, `destination=STS-…`; один APPSEC — несколько STS |

APPSEC-тикет необязателен при создании и редактировании проекта; пустую привязку можно сохранить или очистить. Поиск использует тот же `/api/v1/tasks`, что и раздел Tasks. Выбор сохраняет ключ и URL. При ручной вставке ссылки ключ извлекается из последнего сегмента пути; несовпадение ключа и ссылки или пространство STS отклоняются с 422. Ручной ввод не подтверждает существование тикета на внешнем сервере.

Экспорт уязвимостей в STS требует заполнить в проекте APPSEC-тикет (ключ или URL), логин исполнителя, код продукта, хотя бы один компонент и одну затронутую версию. Интерфейс перед экспортом перечитывает проект и выводит стандартное уведомление со списком недостающих полей; сервер проверяет те же условия до внешнего запроса и возвращает 422. Исполнитель берётся **только** из текущего `project.appsec_assignee`: старый параметр assignee принимается для совместимости и игнорируется. Это не автор экспорта и не неизменяемый исполнитель исходного APPSEC. Отмена создания из Tasks очищает весь черновик, включая продукт и массивы компонентов/версий.

Параметры авторизации общие: `WORKS_ENABLED`, `WORKS_BASE_URL`, `WORKS_API_TOKEN`, `WORKS_COOKIES`, `WORKS_VERIFY_SSL`. Токен браузеру не выдаётся. Настройки пространств независимы: изменение пространства экспорта не должно менять источник Tasks.

Повторный экспорт находки возвращает существующий STS-тикет. Backend сериализует запросы блокировкой находки: два параллельных обращения не создают два тикета. В интерфейсе используется один поток экспорта через окно Task Tracker. При недоступности интеграции показывается понятное сообщение, а диагностика и request ID остаются в логах.

## JSON карточки AS21 и создание проекта

Полная карточка загружается `TaskTrackerService._request` через GET `/rest/api/unit/v2/{key}?validatorEnabled=true`. `WORKS_UNIT_DETAIL_PATH` задаёт шаблон пути относительно базы `/swtr`; `WORKS_UNIT_FIND_PATH` сохранён отдельно для чтения статуса STS через старый find. Авторизация общая: сервисный Bearer и статическая cookie `api_swtr_as21=true`. Ответ полной карточки — прямой unit с массивом attributes, а не строка страницы TQL.

Поддерживаются словари `unit.attributes`/`attrs` и реальный TQL-ответ
`content[].unit` + соседний массив `content[].attributes` с элементами
`{attribute: {code}, value}`. Полная карточка использует `{code, name, value}`;
оба формата нормализуются. При разворачивании unit соседние атрибуты сохраняются.
Статус `statusType=progress` отображается как «в работе», даже если его имя —
«Тестирование». ФИО исполнителя собирается из `lastName/firstName/middleName`,
логин хранится отдельно. Описание берётся из `descriptionPlain`, а при его
отсутствии извлекается из ProseMirror-объекта или JSON-строки. Читаются:

- `assigned_to`: логин строкой либо объект с `username`/`login`/`code` и отображаемым именем. `assignee_username` отделён от `assignee`: отображаемое имя само по себе не считается IAM-логином.
- `affects_version_s`: **весь массив** версий APPSEC `{code,name,status}`; в проект сохраняются code/name. Поддержаны прежние `affects_version_s_crpv` и `affects_version`. Порядок сохранён, дубли кодов удаляются.
- `sber_component`: весь массив компонентов `{code,name}`. `WORKS_APPSEC_COMPONENT_ATTRIBUTE` позволяет заменить исходный код атрибута.
- Код продукта: строка либо taxonomy-объект, откуда используется `value.code`, а не отображаемое `value.name`. Код исходного поля задаётся `WORKS_APPSEC_PRODUCT_CODE_ATTRIBUTE`; если он отличается, поддержан атрибут с именем «Код продукта».

«Создать проект» в Tasks сначала загружает полную карточку тем же `getTask`, затем открывает чистую форму: название из summary, тикет, логин/ФИО исполнителя, код продукта, все компоненты и версии. Частичная строка списка не используется. При выборе APPSEC в форме проекта также загружается полная карточка; существующий исполнитель проекта при этом не подменяется. При отказе показывается безопасное уведомление; поздние ответы после смены ввода/закрытия формы игнорируются. Метаданные остаются снимком; статус связанного проекта синхронизируется отдельно. Новых колонок/полей в интерфейсе Tasks не добавлено.

Миграция 0024 добавляет `projects.appsec_versions` (JSON-массив `{code,name}`) и `appsec_assignee_name`. Старая одиночная версия переносится в массив из одного элемента без изменения названия. Поля `appsec_version_code/name` оставлены как представление первого элемента для старых клиентов; рабочая форма и экспорт используют весь массив. Очистка массива и APPSEC-тикета допустима; после неё экспорт недоступен до заполнения данных.

Миграция 0026 и штатный startup добавляют `appsec_product_code` и массив `appsec_components`. Прежний одиночный компонент переносится в массив; scalar code/name отражают первый элемент для старых клиентов. Обновление названия проекта не обрезает массивы, очистка массива очищает и scalar-представление.

`WorksClient.create_bug_appsec` передаёт все версии в `attributes.affects_version_s_crpv` как code/name и все компоненты в `sber_component` как code/name/title. Названия остаются исходными. Только при заполнении версии в СЗИ убирается название продукта:

| Исходное имя | Версия в отчёте |
| --- | --- |
| `Platform V Stack 1.0.2` | `1.0.2` |
| `Platform V Stack 1.0.2-beta2` | `1.0.2-beta2` |
| `Platform V Stack 1.0.2-beta.2` | `1.0.2-beta.2` |

Версионный суффикс берётся целиком, включая prerelease/build. Для нескольких версий значения перечисляются через запятую. `_report_version`/`_distrib_version` не меняют проект или исходные ссылки версий. В текущем шаблоне ПП отдельного поля версии дистрибутива нет.

## Локальные демо-тикеты

`python -m scripts.seed_ui_demo` создаёт девять нативных JSON units в `backend/.local/task-tracker-demo.json` (каталог исключён из git). Есть разные статусы, отсутствие исполнителя/версии, одна/две/три версии; первый тикет связан с `[DEMO] Полный интерфейс`, если у него ещё не было привязки. Повторный запуск не создаёт проекты-дубли и не перезаписывает вручную заполненную привязку.

Для локального compose: `WORKS_TASKS_DEMO_FILE=/app/.local/task-tracker-demo.json`, `WORKS_ENABLED=false`, затем пересоздать backend для применения env. Tasks показывает пометку «Демо-данные». Справочник версий берётся из тех же fixtures. В этом режиме реальный экспорт отключён, внешние тикеты не создаются; одновременное включение реальной интеграции и fixtures отклоняется с 503. Нет автоматического перехода к демо при отказе внешнего API. На реальном подключении оставляйте `WORKS_TASKS_DEMO_FILE` пустым.

## Настройка поиска задач

По умолчанию используется рабочий запрос браузера AS21: POST
`/rest/api/unit/v3/find/tql` относительно `WORKS_BASE_URL` (обычно база заканчивается
на `/swtr`, второй `/swtr` в path добавлять не нужно). Тело:

```json
{"attributes":["workflow_status","priority","assigned_to","affects_version_s"],"calculatedAttributes":[],"query":"space = \"APPSEC\" and suit = \"security_assessment_appsec\"","page":{"size":20,"page":0},"timeZone":"Europe/Moscow"}
```

К трём атрибутам списка добавлен подтверждённый для APPSEC `affects_version_s`
для получения всех затронутых версий. Не копируйте браузерные `sec-*`, cookie или
`x-tql-batch-id`: сервер использует свою настроенную авторизацию Works.

`WORKS_TASKS_SEARCH_PATH` и `WORKS_TASKS_SEARCH_BODY` позволяют переопределить
этот запрос. Если в `.env.prod` остались старые значения, удалите их для применения
новых defaults либо замените на пример выше. `WORKS_TASKS_SEARCH_BODY` задаётся
одной строкой JSON. Для прежнего структурного фильтра поддерживаются целые
строковые значения `"{space}"`, `"{query}"`, `"{tenant}"`; подстановка внутрь
строки TQL не выполняется. В нативный TQL пользовательский текст не вставляется:
он фильтрует полученную страницу по ключу/названию. Тело без ограничения APPSEC
отклоняется; поддержана точная форма TQL из образца. Дополнительная фильтрация
ответа не допускает попадания STS в Tasks при смешанной выдаче.

Поиск по **полному** ключу `APPSEC-3291` использует GET карточки и не ограничен
первыми 20 строками. Произвольный текст фильтрует загруженную страницу, полного
обхода страниц TQL пока нет.

## Контракт создания STS

Отправляются все поля рабочего bug_appsec-запроса, включая пустые optional-поля.
`space=STS`, `suit=bug_appsec`, `attributes.space=APPSEC`, `tenant=default`.
Код продукта обязателен. Метки — `Vuln_Pentest` и `vuln`, практика —
`security_analysis`, workflow — NEW. Поля resolution, customfield, package,
revised CVSS, external_link и watchers присутствуют с null, как в образце.
Без вложений `draftsInfo=[]`; фиктивный draftId не создаётся. Вложения по-прежнему
предварительно загружаются в реальный черновик.

| Критичность STORM | priority | initial_criticality_cvss |
| --- | --- | --- |
| critical | blocker | `["critical_cvss"]` |
| high | critical | `["high_cvss"]` |
| medium | major | `["medium_cvss"]` |
| low | minor | `["low_cvss"]` |
| info | trivial | `null` |

В `original_cvss` передаётся вектор находки без префикса `CVSS:4.0/`, как в
нативном образце. Никакой массив из всех критичностей одновременно не отправляется.
Ответ `{"id":"STS-…"}` поддержан вместе с code/key. Ключ проверяется перед
сохранением и связыванием. Источник связи — APPSEC, назначение — созданный STS.

Настройка prod и обязательные секреты: [PROD_ENV.md](PROD_ENV.md).

## Справочники формы проекта

Компоненты и версии ищутся через нативные plugin endpoints из
`WORKS_COMPONENT_FIND_PATH` и `WORKS_VERSION_FIND_PATH`. Оба используют
`WORKS_REFERENCE_SPACE=STS`, страницу 0 размера 100 и передают пользовательский
query JSON-строкой. `WORKS_TASKS_SPACE=APPSEC` относится к карточкам и списку
задач, а не к этим справочникам. При автозаполнении из тикета версии по-прежнему
читаются из APPSEC `affects_version_s` и не заменяются результатом справочника.

Отказы внешнего API (включая его 422), таймауты и некорректный JSON возвращают
502 `task_tracker_unavailable`. Неполная конфигурация возвращает 503
`task_tracker_not_configured`. Они не превращаются в 422 бизнес-валидации.
Тайпхед показывает безопасное уведомление один раз за период отказа и позволяет
повторить поиск при изменении ввода. Заголовок «AppSec export (Works)» удалён.

Отсутствие авторизации/базы, явно обнулённое тело поиска или неверное ограничение пространства дают 503 с объяснением, ошибка внешнего HTTP/API или некорректный ответ — 502. 422 при сохранении проекта означает ошибку привязки или входных данных. По одному старому статусу 422 нельзя установить причину ошибки на проде.

Для проверки подключения нужны: URL и метод рабочего запроса из Network интерфейса Task Tracker, обезличенные JSON тела и ответа, `detail` ошибки STORM. Указать значения пространств и путей; для токена/cookie достаточно «задан/не задан». Не присылайте Authorization, Cookie, пароли и сами токены.

Чтобы найти нужный запрос, откройте DevTools → Network → Fetch/XHR **до** перехода
в список задач пространства APPSEC. Перезагрузите список, затем введите текст
поиска. Нужен POST поиска списка (обычно `/rest/api/unit/v3/find`), ответ которого
содержит несколько APPSEC-задач. Запрос карточки с `filters.units=["APPSEC-…"]`,
справочника версий или создания тикета не подходит для `WORKS_TASKS_SEARCH_BODY`.

Передайте метод и URL, JSON из Request Payload и Response с одной обезличенной
задачей и метаданными пагинации. Сохраните имена полей, типы, структуру фильтра
пространства, исполнителя и затронутых версий; удалите персональные значения.
Если фильтр поиска устроен сложно, приложите два тела: без текста поиска и с
тестовым словом — это позволяет определить меняющееся поле без угадывания API.
При Copy as cURL удалите все Authorization, Cookie и другие секретные заголовки;
лучше прислать отдельно только URL и JSON. После настройки значение env хранится
одной строкой JSON, например `WORKS_TASKS_SEARCH_BODY='…'`; форму фильтров берите
из рабочего запроса, а не из выдуманного шаблона.

## Границы проверки

`tests/api/test_tracker_spaces.py` проверяет HTTP STORM, реальный PostgreSQL и сформированные нативным WorksClient запросы через MockTransport: создание STS, связь с APPSEC, смешанную выдачу, детальную карточку, ручную ссылку, неверные/противоречивые значения, замену и очистку привязки, создание без тикета с участником и аудитом и запрет экспорта при любой комбинации недостающих полей. Это не подтверждение доступности внешнего сервера или прав сервисной учётки.

Поиск пока возвращает одну страницу внешнего API; полнота списка зависит от тела поиска (по умолчанию 20 задач). Создание тикета и последующее создание связи — отдельные внешние операции. Если создание связи отказало, экспорт сохраняет STS-тикет и пишет предупреждение в серверный лог. Автоматической повторной связи пока нет. Исправленное направление APPSEC → STS применяется к новым экспортам; уже созданные внешние связи автоматически не изменяются.

Миграция 0023 сохраняет три старые таблицы интеграции под именами `retired_tracker_configs`, `retired_project_tracker_links`, `retired_tracker_issue_links`. Рабочий код их не использует. Исторические миграции оставлены для обновления существующих баз; строки из старых таблиц не удаляются.

## Подсказки кода продукта STS

Форма проекта вызывает `/api/v1/works/product-codes?q=...`. Backend загружает
GET `/rest/api/suit/v1/bug_appsec?validatorEnabled=true` и берёт
`directoryValues` только атрибута `product_code_list_sts`. Названия показываются
в подсказке, сохраняется точный `code`: регистр, числовые идентификаторы и
подчёркивания не преобразуются. Ручной ввод кода остаётся доступным при отказе
справочника; ошибка показывается уведомлением. Код следует брать из STS, а не
из taxonomy `customfield_24900` другой формы.

Полный справочник кэшируется внутри процесса на 60 секунд, максимум для восьми
подключений. Смена URL, пути, атрибута или авторизации исключает использование
прежнего кэша. Поисковый запрос фильтрует кэш локально; ошибки не кэшируются.
Тикет из примера (`unit=STS-217322`) не зашит в конфигурацию.

## Индекс и содержимое STS-тикета

`finding_references` общий для Word и STS: первый компонент проекта, `end_date` в формате `DDMMYY`, сквозной номер уязвимости/слабости. Unrealized пропускаются. Пункт берётся из структуры шаблона, включая номер стенда. `WORKS_REPORT_KIND=szi` по умолчанию, `pp` — для ПП; настройка необязательна. Дата окончания остаётся необязательной для сохранения проекта, но требуется для STS-экспорта.

Описание состоит строго из трёх строк:

```text
Провести анализ и устранить уязвимость SA-EVPC-201126/01, выявленную в ходе проведения анализа защищенности.
Информация по уязвимости отправлена в почту ВП.
Пункт в отчете - 4.5.1.1
```

Произвольное описание, шаги, влияние, рекомендации и файлы находки не читаются для отправки; `draftsInfo` пуст. Указанная фраза о почте — шаблонный текст, отправку письма STORM при этой операции не выполняет. Список находок возвращает сохранённые `task_tracker_issue_key/url` одним пакетным запросом; UI открывает их напрямую.

Статус связанного проекта синхронизируется отдельно от снимка метаданных: см. [TASKS_AND_PERMISSIONS.md](TASKS_AND_PERMISSIONS.md).


## Отсутствующий тикет

`GET /tasks/{key}` возвращает 404 с `detail: Тикет не найден`, `code: not_found` и `request_id`, когда карточка отсутствует, вернулся пустой результат или ключ не принадлежит APPSEC. В UI отображается локализованное «Тикет не найден». Отказ авторизации, 5xx и отсутствующий endpoint поиска остаются ошибками подключения, а не ошибкой отсутствия тикета.
