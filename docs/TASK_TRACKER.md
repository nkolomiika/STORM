# Task Tracker: STS и APPSEC

Приложение использует нативный API Task Tracker/Works и настройки `WORKS_*`.

| Операция | Пространство | Код и связь |
| --- | --- | --- |
| Экспорт уязвимости | `WORKS_SPACE=STS` | POST `WORKS_CREATE_PATH`, тип `bug_appsec`; space задан также в attributes |
| Раздел Tasks и поиск тикета для проекта | `WORKS_TASKS_SPACE=APPSEC` | POST `WORKS_TASKS_SEARCH_PATH`; в выдаче допускаются только ключи `APPSEC-<число>` |
| Карточка задачи | APPSEC | `WORKS_UNIT_FIND_PATH`, фильтр `units=[key]`; ключ другого пространства отклоняется до сети |
| Привязка проекта | APPSEC | `projects.appsec_ticket_key` и `appsec_ticket_url`; это тикет запроса на анализ, а не экспортированная уязвимость |
| Связь после экспорта | STS → APPSEC | POST `WORKS_LINK_PATH`: `source=STS-…`, `destination=project.appsec_ticket_key` |

APPSEC-тикет необязателен при создании и редактировании проекта; пустую привязку можно сохранить или очистить. Поиск использует тот же `/api/v1/tasks`, что и раздел Tasks. Выбор сохраняет ключ и URL. При ручной вставке ссылки ключ извлекается из последнего сегмента пути; несовпадение ключа и ссылки или пространство STS отклоняются с 422. Ручной ввод не подтверждает существование тикета на внешнем сервере.

Экспорт уязвимостей в STS требует заполнить в проекте APPSEC-тикет (ключ или URL), логин исполнителя и хотя бы одну затронутую версию. Интерфейс перед экспортом перечитывает проект и выводит стандартное уведомление об ошибке со списком недостающих полей; сервер проверяет те же условия до любого внешнего запроса и возвращает 422. Параметр assignee в запросе экспорта не заменяет отсутствующего исполнителя проекта. Отмена создания из Tasks не переносит заполненные поля в обычную форму нового проекта.

Параметры авторизации общие: `WORKS_ENABLED`, `WORKS_BASE_URL`, `WORKS_API_TOKEN`, `WORKS_COOKIES`, `WORKS_VERIFY_SSL`. Токен браузеру не выдаётся. Настройки пространств независимы: изменение пространства экспорта не должно менять источник Tasks.

## JSON карточки AS21 и создание проекта

Исходный путь карточки находится в `TaskTrackerService._request`: POST `WORKS_UNIT_FIND_PATH` (по умолчанию `/rest/api/unit/v3/find`) с `filters.units=[key]` и страницей размера 1. Запрос отправляется `WorksClient`, который добавляет Bearer и статическую cookie `api_swtr_as21=true`. `get_task` извлекает нативный unit из ответа; `task_out` проецирует его в карточку.

Из `unit.attributes` (либо `attrs`) читаются:

- `assigned_to`: логин строкой либо объект с `username`/`login`/`code` и отображаемым именем. `assignee_username` отделён от `assignee`: отображаемое имя само по себе не считается IAM-логином.
- `affects_version_s_crpv`: **весь массив** ссылок `{code, name/title}`. Для старого формата поддержан `affects_version`. `affected_versions` сохраняет порядок, одинаковые коды не дублируются.

«Создать проект» в Tasks сначала загружает полную карточку тем же `getTask`, затем открывает форму с тикетом, исполнителем и всеми версиями. Частичная строка списка не используется вместо полной карточки. При отказе загрузки форма не открывается; поздний ответ после ухода из Tasks игнорируется. Поля можно изменить перед сохранением. Это снимок при создании, последующие изменения тикета автоматически не перезаписывают проект.

Миграция 0024 добавляет `projects.appsec_versions` (JSON-массив `{code,name}`) и `appsec_assignee_name`. Старая одиночная версия переносится в массив из одного элемента без изменения названия. Поля `appsec_version_code/name` оставлены как представление первого элемента для старых клиентов; рабочая форма и экспорт используют весь массив. Очистка массива и APPSEC-тикета допустима; после неё экспорт недоступен до заполнения данных.

`WorksClient.create_bug_appsec` передаёт весь массив в `attributes.affects_version_s_crpv`; коды, `name` и `title` остаются исходными. Только при заполнении версии в СЗИ убирается название продукта:

| Исходное имя | Версия в отчёте |
| --- | --- |
| `Platform V Stack 1.0.2` | `1.0.2` |
| `Platform V Stack 1.0.2-beta2` | `1.0.2-beta2` |
| `Platform V Stack 1.0.2-beta.2` | `1.0.2-beta.2` |

Версионный суффикс берётся целиком, включая prerelease/build. Для нескольких версий значения перечисляются через запятую. `_report_version`/`_distrib_version` не меняют проект или исходные ссылки версий. В текущем шаблоне ПП отдельного поля версии дистрибутива нет.

## Локальные демо-тикеты

`python -m scripts.seed_ui_demo` создаёт девять нативных JSON units в `backend/.local/task-tracker-demo.json` (каталог исключён из git). Есть разные статусы, отсутствие исполнителя/версии, одна/две/три версии; первый тикет связан с `[DEMO] Полный интерфейс`, если у него ещё не было привязки. Повторный запуск не создаёт проекты-дубли и не перезаписывает вручную заполненную привязку.

Для локального compose: `WORKS_TASKS_DEMO_FILE=/app/.local/task-tracker-demo.json`, `WORKS_ENABLED=false`, затем пересоздать backend для применения env. Tasks показывает пометку «Демо-данные». Справочник версий берётся из тех же fixtures. В этом режиме реальный экспорт отключён, внешние тикеты не создаются; одновременное включение реальной интеграции и fixtures отклоняется с 503. Нет автоматического перехода к демо при отказе внешнего API. На реальном подключении оставляйте `WORKS_TASKS_DEMO_FILE` пустым.

## Настройка поиска задач

`WORKS_TASKS_SEARCH_BODY` — JSON-объект из рабочего запроса поиска вашего экземпляра Task Tracker. Форма фильтра не угадывается: API разных установок может отличаться. В фильтре пространства замените значение APPSEC на строку `"{space}"`, а значение поиска — на `"{query}"`; при необходимости доступен `"{tenant}"`. Заменяются только целые строковые значения, пользовательский запрос остаётся JSON-данными. Тело без указания пространства APPSEC или `{space}` не отправляется. Дополнительная фильтрация ответа не допускает попадания STS в Tasks, даже если сервер вернул смешанный список.

Отсутствие настройки/тела поиска даёт 503 с объяснением, ошибка внешнего HTTP/API или некорректный ответ — 502. 422 при сохранении проекта означает ошибку привязки или входных данных. По одному старому статусу 422 нельзя установить причину ошибки на проде.

Для проверки подключения нужны: URL и метод рабочего запроса из Network интерфейса Task Tracker, обезличенные JSON тела и ответа, `detail` ошибки STORM. Указать значения пространств и путей; для токена/cookie достаточно «задан/не задан». Не присылайте Authorization, Cookie, пароли и сами токены.

## Границы проверки

`tests/api/test_tracker_spaces.py` проверяет HTTP STORM, реальный PostgreSQL и сформированные нативным WorksClient запросы через MockTransport: создание STS, связь с APPSEC, смешанную выдачу, детальную карточку, ручную ссылку, неверные/противоречивые значения, замену и очистку привязки, создание без тикета с участником и аудитом и запрет экспорта при любой комбинации недостающих полей. Это не подтверждение доступности внешнего сервера или прав сервисной учётки.

Поиск пока возвращает одну страницу внешнего API; полнота списка зависит от тела поиска. Создание тикета и последующее создание связи — отдельные внешние операции. Если создание связи отказало, экспорт сохраняет STS-тикет и пишет предупреждение в серверный лог. Автоматической повторной связи пока нет.

Миграция 0023 сохраняет три старые таблицы интеграции под именами `retired_tracker_configs`, `retired_project_tracker_links`, `retired_tracker_issue_links`. Рабочий код их не использует. Исторические миграции оставлены для обновления существующих баз; строки из старых таблиц не удаляются.
