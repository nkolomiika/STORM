# Архитектурное ревью STORM

Проверка 10–13 ноября 2026 года охватывает HTTP, сервисы, ORM, загрузку данных React, миграции, аудит и WebSocket. Исправлены подтверждённые узкие места. После команды владельца «фикси все» устранены и шесть согласовывавшихся логических дефектов; выбранное поведение и регрессии приведены ниже.

## Что исправлено

| Узкое место | Изменение | Подтверждение |
| --- | --- | --- |
| SELECT упоминаний внутри цикла комментариев | Один запрос по ID комментариев страницы | Для 100 комментариев 106 → 7 SQL вместе с авторизацией и проверками; тест проверяет mentions каждой строки |
| Отдельные запросы автора/проекта/находки каждого уведомления | Общая загрузка по трём видам контекста | Для 100 событий проекта 203 → 4 SQL; смешанный набор контекстов покрыт тестом |
| Проверка хоста загружает всё его дерево | `_ensure_host` читает только Host.id и project_id | Чтение портов 9 → 5 SQL, эндпоинтов 8 → 4; тест исключает запросы endpoints/IP при чтении портов |
| Каждая страница JS читает все имена хостов проекта | Lookup только по host_id текущей страницы | Сохранены hostname и объём ответа; тест проверяет ограничение IDs |
| Список находок делает запрос полной карточки на каждую строку | `affected_host_id` в списке и локальное сопоставление имён | Удалены до 100 дополнительных HTTP GET; перечитывание хостов больше не запускает загрузку находок |
| Иерархия хостов считается повторными попарными сравнениями | Индекс суффиксов + useMemo | Сравнение с прежним алгоритмом, тест на 5 000 строк; [микробенчмарк](performance/host-index.json) |
| Нет индексов `ports.host_id` и `services.port_id` | Индексы ORM и concurrent Alembic-миграция | EXPLAIN: Seq Scan → Index Scan; реальный тест upgrade/downgrade и повторного upgrade |
| Крупные списки сериализуются как общий dict | Типизированные `PaginatedResponse` для hosts, JS, comments, notifications, vulnerabilities | Контракт полей сохранён; OpenAPI теперь описывает эти ответы; общего большого ускорения списка хостов не заявляется |
| Графики проектов скачивают все деревья хостов только ради дат | Отдельный SELECT created_at и защищённый метод host-creation-times | На 5 000 хостов 52,8 МБ → 150 КБ, 225 → 3 SQL; состав и порядок дат совпадают |
| Списки эндпоинтов пересоздаются при несвязанных изменениях формы | useMemo для плоского списка и отфильтрованных групп | Смена данных/фильтров продолжает пересчитывать списки; UI-регрессии проходят |

Изменения находятся в `services.py`, соответствующих routers, `models.py`, миграции `0020`, `StormApp.tsx` и `hostIndex.ts`. Показатели до/после и условия эксперимента: [PERFORMANCE.md](PERFORMANCE.md).

## Дополнение 11 ноября: устранённые технические сбои

Исправлены авторизация WebSocket (строковый JWT sub раньше приводил к ошибке PostgreSQL INTEGER/VARCHAR) и изменение множества подключений во время await рассылки. Используются общий decode_token и снимки наборов адресатов. Это локальные исправления одного процесса; вопрос доставки между workers ниже остаётся открытым.

Скачивание файлов/JS-архивов с Unicode-именами переведено на UTF-8 filename*, в Word-отчётах исправлен ASCII fallback. Ранее русские имена вызывали HTTP 500 при создании заголовка ответа. Регрессии не вызывают внешнее хранилище или сеть.

Для ранее неработавшей кнопки Post comment создан отдельный модуль EndpointCommentService, таблица и миграция 0021, защищённые GET/POST и компонент EndpointDiscussion. Автор подгружается JOIN, размер страницы ограничен, запись и аудит новой операции атомарны. 13 ноября аналогичная гарантия сущность/аудит распространена на внутренние CRUD старых сервисов.

В формах активации, восстановления пароля и возврата аккаунта смена токена теперь сбрасывает старую форму и запускает проверку новой ссылки. Ответ проверки доступности прежнего имени игнорируется. При использовании одноразовой ссылки строка токена блокируется до commit, чтобы параллельная отправка не могла использовать её повторно. Некорректные скобки в URL цели фермы отклоняются парсером без необработанного ValueError.

Атомарность внутренних CRUD не означает общую транзакцию с MinIO, Jira/Works или брокером. Фермы сохраняют результаты по ходу сканирования; ранее завершённые шаги не откатываются из-за отказа последующего шага. Доставка WebSocket между процессами и transactional outbox остаются отдельными архитектурными работами.

## Ограничения больших данных, которые остаются

### Полные графы хостов и загрузка всего проекта

Страница из 200 хостов на выбранных данных содержит 4 000 эндпоинтов с request body/headers и отвечает примерно 2,1 МБ. Внутри проекта `getHosts` последовательно вычитывает все страницы, а JS-loader собирает все JS-файлы проекта. Главная страница для графиков теперь использует лёгкий список дат и не скачивает эти деревья. Размер HTTP-страницы по-прежнему не ограничивает общий объём данных открытого проекта в UI.

При 24 одновременных клиентах p95 такого списка достигает 5,66 с, около 6,75 запросов/с в измеренном процессе. Количество SQL постоянно; узкое место уже не N+1. cProfile фиксирует 24 008 созданий ORM-объектов на четыре обращения к hosts_200 (один прогрев и три измерения). Профиль включает подготовку данных и запуск Python; его времена нельзя напрямую сравнивать с обычным прогоном.

Следующий архитектурный шаг: отдельная компактная модель строки хоста с агрегированными счётчиками; страницы IP и эндпоинтов с серверными фильтрами; полные headers/body только при открытии редактора; виртуализация длинных таблиц. Это требует согласованной миграции UI: сейчас экспорт, фильтры, группировка и метрики опираются на полный локальный набор. Простая замена списка неполной страницей сделает их некорректными.

### WebSocket и горизонтальное масштабирование

`ConnectionManager.rooms/user_sockets` — память процесса. Событие, возникшее в одном Uvicorn worker или отдельном recon worker, не доставляется автоматически в соединения другого процесса. Поэтому увеличение `--workers` само по себе не является завершённым масштабированием приложения.

Нужен общий канал событий между процессами, локальная доставка в комнаты каждого worker и стратегия повторного получения актуальных данных после переподключения. Для операций с обязательной доставкой событие следует фиксировать в outbox одной транзакцией с изменением. В этом проходе доставка между процессами не менялась и внешние брокерные сценарии не тестировались.

### Схема при запуске

Startup выполняет DDL и массовые UPDATE независимо от Alembic. На больших таблицах и при одновременном старте нескольких процессов это создаёт дополнительную работу и конкуренцию за блокировки. Новые индексы вынесены в concurrent-миграцию; существующая историческая инициализация не переписана вслепую.

Нужен отдельный этап миграций перед запуском приложения, перенос исторических преобразований в ревизии и упрощение startup до проверок готовности. Перед таким переносом нужно сверить схемы используемых стендов и их `alembic_version`, поскольку текущий код поддерживает базы, обновлённые через startup.

### Границы модулей и состояние UI

Большая часть бизнес-логики находится в одном `services.py`, а страницы, запросы, редакторы и вычисляемые представления — в `StormApp.tsx`. Общие изменения состояния запускают вычисления всего экрана. Исправление индекса хостов и отделение загрузки находок от обновлений хостов уже сокращают эту работу.

Дальнейшее разделение: сервисы по предметным областям; hooks данных проекта отдельно от редакторов и таблиц; серверные агрегаты для Overview; общий слой запросов с отменой/дедупликацией. Выделять модули лучше по одному сценарию, сохраняя существующие HTTP- и UI-регрессии. Массовое перемещение файлов без изменения границ ответственности не устраняет нагрузку.

### Пул, offset и наблюдаемость

Текущий async engine использует стандартный пул SQLAlchemy; в бенчмарке это 5 постоянных + 10 дополнительных соединений. При 24 клиентах часть запросов ожидает освобождения соединения. Простое увеличение пула не ускорит создание тысяч ORM-объектов и может увеличить нагрузку PostgreSQL.

Глубокая offset-пагинация и точный count требуют отдельного измерения на распределении реального проекта; текущая нагрузка использует первую страницу. Следующий этап — стабильный порядок с ID, keyset-пагинация там, где подходит UX, EXPLAIN на фактических фильтрах и метрики ожидания пула, времени SQL, размера ответа и отставания worker. Эти изменения не объявляются уже проверенными или внедрёнными.

## Границы проверки

Измерено внутреннее чтение девяти HTTP-сценариев через TCP с PostgreSQL: хосты, порты, эндпоинты, комментарии, уведомления, JS, находки, статистика проектов. Есть функциональные CRUD-тесты, но не измерена пропускная способность массовой записи. Не проводились длительный soak-тест, браузерный E2E на 100 000 DOM-строк, сетевые сканы, SMTP, SSO, Works/Jira и MinIO. Это локальная архитектурная диагностика и воспроизводимые регрессии, а не гарантия производственной ёмкости.
